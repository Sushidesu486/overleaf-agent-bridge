# Git integration reference

Research date: 2026-11-14. Scope: direct local `git clone`, `pull`, and `push` against an Overleaf project. GitHub synchronization is a later, separate integration. This note records official documentation and public source inspection; no service was changed or build/runtime experiment performed.

## Findings that change the implementation plan

1. **The official Git bridge core is public and reusable.** It exists in the current `overleaf/overleaf` monorepo, under `services/git-bridge`, with a component-level MIT license. The archived `writelatex-git-bridge` repository points to this migration; it is not the only available source. Prefer evaluating the maintained Java/JGit service with a CE adapter before writing another Git protocol implementation. [Core source](https://github.com/overleaf/overleaf/tree/e039ad26c5bf5422eb57b89fc7e57c75055e631d/services/git-bridge), [component license](https://github.com/overleaf/overleaf/blob/e039ad26c5bf5422eb57b89fc7e57c75055e631d/services/git-bridge/LICENSE), [archived repository](https://github.com/overleaf/writelatex-git-bridge).
2. **Official turnkey deployment remains a Server Pro feature.** Toolkit starts a separate `quay.io/sharelatex/git-bridge` image; the bridge calls a web Snapshot API and token validator. The public web module tree has no corresponding Git bridge/OAuth implementation module. A CE integration needs those contracts implemented or adapted; setting `GIT_BRIDGE_ENABLED=true` alone is insufficient. [Server configuration](https://docs.overleaf.com/on-premises/configuration/overleaf-toolkit/server-pro-only-configuration/git-integration), [public web modules](https://github.com/overleaf/overleaf/tree/e039ad26c5bf5422eb57b89fc7e57c75055e631d/services/web/modules).
3. **Public source and the deployed image require separate version records.** The project records CE 6.3.2 image revision `370f4763da4bc910da8309c9a71c85ecbe39f6a7`. GitHub's public tree API did not resolve that revision during this research; there is also no public `6.3.2` tag. The inspected public revision is `e039ad26c5bf5422eb57b89fc7e57c75055e631d`. Compatibility with the exact deployed image remains an implementation check, not an established result. [Public commit](https://github.com/overleaf/overleaf/commit/e039ad26c5bf5422eb57b89fc7e57c75055e631d), [local version evidence](progress.md).

## Official product behavior to reproduce

The current documentation uses one exposed branch, `main`; older repositories can retain `master`. Web edits produce commits lazily on fetch/pull. A history label can create a distinct commit when no later commit has already passed that history point. Aggregated web edits use the most recent editor as Git author. Overleaf History therefore remains the detailed collaboration record. Git integration excludes tags, Git LFS and contained submodules; execute bits are not preserved and symlinks become regular files. File moves/renames become delete/create operations, potentially losing comments and tracked changes; ordinary Git pushes can also displace that metadata. [Git integration](https://docs.overleaf.com/integrations-and-add-ons/git-integration-and-github-synchronization/git-integration).

Users open **Integrations → Git**, copy the clone URL, and authenticate with username `git` and a personal Git token as password. Tokens belong to users, apply to their accessible projects, can be revoked, and are only fully shown when generated. The official service permits ten tokens per user with one-year expiry. Collaborators obtain their own accounts/tokens. For Server Pro, the URL shape is `https://<site>/git/<projectId>`. [Authentication flow](https://docs.overleaf.com/integrations-and-add-ons/git-integration-and-github-synchronization/git-integration/git-integration-authentication-tokens).

Local branches can be pushed explicitly to the exposed branch, for example `git push overleaf feature:main`. A local repository may have both `overleaf` and a second GitHub/GitLab remote, without a direct server-to-server connection. This satisfies local-agent editing independently of GitHub App setup. [Advanced operations](https://docs.overleaf.com/integrations-and-add-ons/git-integration-and-github-synchronization/git-integration/advanced-git-operations).

## Reusable core and actual dependencies

The inspected `pom.xml` specifies **Java 21**, JGit 7.5, Jetty 12 and ordinary Maven dependencies. It declares no private Maven repository or local proprietary dependency. The README still says JDK 8 and references an old Dockerfile workflow, so use the POM and current build infrastructure when constructing a reproducible image. This is static dependency inspection; an independent Maven build still needs to be run. [POM](https://github.com/overleaf/overleaf/blob/e039ad26c5bf5422eb57b89fc7e57c75055e631d/services/git-bridge/pom.xml), [README](https://github.com/overleaf/overleaf/blob/e039ad26c5bf5422eb57b89fc7e57c75055e631d/services/git-bridge/README.md).

The core already supplies HTTP Git handling, JGit receive hooks, repository storage, SQLite version bookkeeping, snapshot conversion, attachment downloads, project locks and postback coordination. Paid runtime endpoints are not intrinsically required by the Java interfaces: a compatible adapter can implement their HTTP contracts. The official prebuilt Server Pro deployment uses commercial distribution credentials, so a self-built image must have its own pinned build and license notices. [Bridge](https://github.com/overleaf/overleaf/blob/e039ad26c5bf5422eb57b89fc7e57c75055e631d/services/git-bridge/src/main/java/uk/ac/ic/wlgitbridge/bridge/Bridge.java), [SnapshotApi interface](https://github.com/overleaf/overleaf/blob/e039ad26c5bf5422eb57b89fc7e57c75055e631d/services/git-bridge/src/main/java/uk/ac/ic/wlgitbridge/bridge/snapshot/SnapshotApi.java), [Server Pro distribution](https://github.com/overleaf/toolkit/blob/master/doc/getting-server-pro.md).

Current environment defaults are 2,000 files and 52,428,800 bytes per file. These are bridge configuration values, separate from this project's 50,000,000-byte MCP attachment limit and 2,000,000-byte text limit. Boundary enforcement needs explicit alignment: at least one snapshot import check uses `size >= maxSize`. The class named `GitLfsHandler` returns HTTP 422 with an unsupported message; its presence is not LFS support. [Defaults](https://github.com/overleaf/overleaf/blob/e039ad26c5bf5422eb57b89fc7e57c75055e631d/services/git-bridge/conf/envsubst_template.json), [LFS handler](https://github.com/overleaf/overleaf/blob/e039ad26c5bf5422eb57b89fc7e57c75055e631d/services/git-bridge/src/main/java/uk/ac/ic/wlgitbridge/server/GitLfsHandler.java).

### Concurrent editing and push acceptance

`WLReceivePackFactory` explicitly expects web edits during a push to make the operation fail and be retried. `WriteLatexPutHook` checks the repository's actual HEAD branch, rejects non-fast-forward updates, calls the bridge before accepting the Git update, and maps `OutOfDateException` to a non-fast-forward rejection. [Receive-pack factory](https://github.com/overleaf/overleaf/blob/e039ad26c5bf5422eb57b89fc7e57c75055e631d/services/git-bridge/src/main/java/uk/ac/ic/wlgitbridge/git/handler/WLReceivePackFactory.java), [pre-receive hook](https://github.com/overleaf/overleaf/blob/e039ad26c5bf5422eb57b89fc7e57c75055e631d/services/git-bridge/src/main/java/uk/ac/ic/wlgitbridge/git/handler/hook/WriteLatexPutHook.java).

`Bridge.push` holds its project lock, sends the candidate, waits for the web postback, then advances its version bookkeeping. Its lock implementation is an in-process `ReentrantLock` with a five-second acquisition attempt, not a lock shared with the editor. Therefore **the adapter must enforce the project version and its write barrier against web/MCP mutations**. Official deployment guidance also describes the Git bridge as a singleton with local repositories. [Lock implementation](https://github.com/overleaf/overleaf/blob/e039ad26c5bf5422eb57b89fc7e57c75055e631d/services/git-bridge/src/main/java/uk/ac/ic/wlgitbridge/data/ProjectLockImpl.java), [official scaling guidance](https://github.com/overleaf/overleaf/wiki/Horizontal-Scaling).

## Proposed engineering decisions, subject to prototype

- Reuse the public Java service in an isolated development image. Build a narrow native CE Snapshot API adapter and personal Git credential UI. Keep Git credentials separate from MCP capability URLs; validate the current user's project role for every read/write request.
- Present one branch and ordinary Git conflict handling. Preserve client commits as supplied, while recording the authenticated pusher independently in application audit/history. A Git author field alone does not establish who authenticated.
- Give a snapshot a real immutable project revision, including tree structure and attachment identities. Reusing a document's version number as the whole-project version would miss changes elsewhere.
- Make a push one recoverable project operation. Stage content and validate all paths/limits before entering the native write barrier; recheck the base revision under that barrier; apply through the native document/entity/history mechanisms; persist the result before acknowledging it. Design timeout/crash reconciliation for the interval between editor application, postback and Git ref completion.
- Preserve normal `.tex`, `.bib`, image and PDF blobs; reject unsupported Git modes/LFS pointers explicitly. Match the existing decoded file limits and add a separate aggregate push budget. Avoid lossy MIME-based transformations during Git round trips.
- First prove: clone → web edit → pull; local text/binary/add/delete push → live editor and compile; stale push rejection; read-only member push denial; token revoke; interrupted push reconciliation. Then add history labels and detailed attribution behavior.

If adapting the official core proves more complex than expected, native Git's `http-backend` provides the smart HTTP transport, and pre-receive hooks can reject a push before ref updates. It still requires the same snapshot, permission, version and recovery adapter; implementing transport alone would not complete the feature. [Git HTTP backend](https://git-scm.com/docs/git-http-backend), [receive hooks](https://git-scm.com/docs/githooks).

## Future GitHub remote: keep separate

Official GitHub synchronization is a manual push/pull workflow: project owners establish the link, incoming conflicts create a dated branch to merge, and existing project ↔ existing repository linking is unsupported. It does not expose general branch management or LFS. Current docs warn that synchronization stops when editable files total more than 7 MB; this is a hosted synchronization product limit, not a limit to inherit for our direct Git remote. [GitHub synchronization](https://docs.overleaf.com/integrations-and-add-ons/git-integration-and-github-synchronization/github-synchronization).

Later server-side GitHub operations can use a GitHub App. Installation tokens act as the App and are scoped to its installation/repositories; user tokens additionally intersect the user's permissions and attribute the API activity to that user. Neither is necessary for local Git against our service. [Installation authentication](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/authenticating-as-a-github-app-installation), [user authentication](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/authenticating-with-a-github-app-on-behalf-of-a-user).

For that later adapter, GitHub GraphQL `updateRefs` provides an exact `beforeOid` precondition and atomic ref updates. REST `update-ref` with `force:false` enforces fast-forward ancestry but does not accept an expected old head. This distinction matters if a future GitHub sync uses optimistic concurrency. [GraphQL refs](https://docs.github.com/en/graphql/reference/git#updaterefs), [REST refs](https://docs.github.com/en/rest/git/refs#update-a-reference).
